# One mission at a time to a browser guest

Last verified: 2026-11-21 against `fork/main` `7b562b378fc6c5ffc10a2e181813725720ed3925`. This is a research note, not a shipped design. It follows the direction accepted in [ADR 0005](../adr/0005-mission-scoped-content.md); [ADR 0003](../adr/0003-browser-is-a-guest.md) still binds the browser to guest-only authority.

Question: can the host hand a browser guest one mission instead of the whole ~1.1 GB retail `DATA`, and still cover every mission a native host can run?

Verdict: **the dependency graph for one mission already exists in the converter and in `datadir.bin`, but neither the shipping web manifest, the ticket, nor the Full guest path can express a subset today.** Per-mission delivery is a schema and verification change on top of an existing per-mission closure, not a new dependency resolver. Whether the whole closure can be *published* for licensed Full data is a separate, unproved question.

## 1. Smallest correct unit: boot index + per-mission dependency closure

- **Claim: the converter already computes a per-mission closure keyed by mission basename.** `mission_planning::plan_missions` iterates `cpf.missions`, takes `Levels/<proto>.rhp` + `Levels/<mission>.rhm`, parses them, and collects script (`.scb`), descriptor (`.red` via `res_descr::red_filename`), `Text/Level.res` dialogue samples, music names, sound wave ids, ambiance, forest flag, map names and reachable RHS profiles into a `ShippingMissionBuild` inserted under `mp.mission_filename` (`mission_planning.rs:233-495`, especially `:276-315`, `:323-345`, `:393-490`). `MissionProfile` carries exactly `proto_level_filename` / `mission_filename` (`crates/robin_level_data/src/profiles.rs:763-766`), and ticket mission ids are validated as safe basenames (`crates/robin_engine/src/multiplayer.rs:350-361`).
- **Claim: that closure is materialised as a list of shipped files.** `MissionPackaging::package` starts with `missions/<filename>`, then appends terrain payloads, RHS chunks for required profiles, common audio, exclamation metadata, per-actor voice files, dialogue audio, ambience and music; it sorts/dedups and registers `dd.missions[mission] = ShippingMissionRef { forest_level, files }` (`shipping_phases.rs:460-526`). `ShippingMissionRef.files` is documented as paths relative to `datadir.bin`, with shared RHS/terrain named by several missions without duplication (`shipping_datadir.rs:390-400`). The same list is copied into `dependency_plan.missions[mission].destination_payloads` (`convert_datadir.rs:1679-1689`; type at `dependency_plan.rs:31-36`).
- **Claim: the runtime resolves exactly that list, deterministically, from the mission plus the selected profile closure.** `required_dependencies` starts from `datadir.mission_ref(mission).files`, adds authored exclamation ids, walks `campaign.mission_team_indices` and non-instanced `campaign.gang_indices` through `character_rhs_files`, `character_audio_files` and `character_exclamation_ids` (normalising RobinHood/RobinTown against `forest_level`), and adds `saved_world_rhs_files` only when a decoded save is present (`planning.rs:28-130`, `:132-163`). `mission_profile_id` is signed in the ticket (`join_ticket.rs:51`) and copied into the guest's launch (`main_entry/cli.rs:447-452`); the team/gang indices come from the guest's campaign state, not from the ticket.
- **Claim: boot and per-mission bytes are already separate.** `datadir.bin` is the boot manifest (profiles, shared UI/text resources, descriptors, sprite-bank dictionaries, mission dependency graph, character indexes, save-world closure, locales) (`shipping_datadir.rs:58-113`; `docs/COMPRESSION.md:429-437`). Per-mission payloads hold the parsed level/script, terrain/minimap and loading resources (`docs/COMPRESSION.md:429-434`; `shipping_datadir.rs:402-416`). `wasm_boot` decodes only `datadir.bin` and installs it globally; split files are staged separately by `wasm_preload_shipping_file` (`robin.rs:314-345`, `:382-402`).
- **Truly shared vs mission-specific (from the packaging list above):** shared = `datadir.bin`, boot overlay assets, wasm/JS, `rhs/` chunks, `terrain/` maps, `audio/bundles` common effects and exclamation metadata, `audio/assets` content-addressed Opus files, `cinematics/assets`, the boot sprite dictionaries. Mission-specific = one `missions/<mission>.rhmission.zst` (level + script), that mission's terrain/minimap/PAK keys, its dialogue and music audio, its authored exclamation ids, and the subset of `rhs/`/`audio/` reachable through its team and gang roster (`shipping_phases.rs:476-504`; `docs/COMPRESSION.md:811-825`).
- **Unproved:** the exact shared/mission-specific byte split for a current official fullgame conversion. No committed `robinhood-web-content.json` or `conversion-plan.json` fixture exists in this tree (`find` over the worktree returned none). `docs/COMPRESSION.md:811-837` reports a 2026-08-28 measured `H01_Lin_VL` artifact (boot datadir 9,352,150 B; boot game payload 14,186,872 B; 59 blocking mission files 26,142,522 B; audio played through startup 1,322,900 B), but those numbers are not tied to the current schema (`shippingDatadirSchema` 24, `wasm-www/runtime-contract.json`).

## 2. Can `WebContentManifest` express per-mission sets? No — a schema change is required

- **Claim: the manifest is a whole-package, exact-set format.** `WebContentManifest` has exactly `schema`, `edition`, `engine_version`, `native_content_sha256`, `datadir`, `files` with `#[serde(deny_unknown_fields)]`; schema is pinned to `2` and `WebContentFileKind` has only `Shipping` and `Asset` (`content_identity.rs:38-82`). `write_web_content_manifest` walks every regular file under `data_out`, sorts them, puts `datadir.bin` in `datadir` and everything else in `files`, and bails if `files` is empty (`packaging.rs:7-123`). `verify_web_content_package` requires the package directory to contain exactly the declared files — missing or extra files fail (`content_identity.rs:293-347`, test at `:558-625`).
- **Claim: the browser Full path demands that exact set.** `parseLocalManifest` uses `exactObject` on the same six keys, checks `schema`/`edition`/`engine_version`, per-file length and digest, and a 2 GiB total (`multiplayer_content.ts:240-294`). `loadExactFull` checks the selected folder has exactly the manifest-listed paths, verifies the manifest digest against the build manifest, verifies `native_content_sha256` against the ticket, and hashes each file (`multiplayer_content.ts:326-373`). The publishing verifier additionally requires all four buckets `audio`, `missions`, `rhs`, `terrain`, canonical JSON and strictly sorted paths (`verify-datadir-corpus.mjs:187-280`).
- **Claim: the Demo path does not use the manifest at all.** It downloads one signed blob and compares its digest/byte length to the build manifest, then sets `dataBaseUrl` to the blob's directory (`multiplayer_content.ts:100-123`, `:200-221`). There is no per-file list on that path.
- **Needed change (claim, not implemented):** add a per-mission catalog to the manifest (e.g. `missions: { <mission_id>: { files: [path, ...] } }` or a separate signed catalog keyed by a bundle digest), bump `WEB_CONTENT_MANIFEST_SCHEMA` (2 → 3), the web runtime `contentSchema` (`wasm-www/runtime-contract.json`, currently 2), `parseLocalManifest`/`parseWebContentManifest` exact-key lists, and relax the "all four buckets / exact whole package" check into "exact bundle set". The per-mission input already exists in `dependency_plan.missions[*].destination_payloads` and `dd.missions[*].files` (`convert_datadir.rs:1679-1689`); `conversion-plan.json` is explicitly excluded from the web package as a diagnostic (`packaging.rs:75-78`, `convert_datadir.rs:1690-1691`).
- **Unproved:** which schema shape the build pipeline should publish; whether to publish one catalog with all missions or one small manifest per mission. Both are design choices, not facts from code.

## 3. What the host must sign

- **Claim: the ticket already signs mission id, profile id and the whole-installation content identity.** `BrowserJoinTicketPayload` includes `content_edition`, `content_identity_sha256`, `mission_id`, `mission_profile_id` under a `v3` signing domain, and `validate_static_payload` checks the digest format and mission-id safety (`join_ticket.rs:26`, `:35-53`, `:82-131`, `:387-397`). The browser parses the same fixed key set and signature (`join_ticket.ts:12-28`, `:32-48`, `:108-175`).
- **Claim: that identity is the whole native closure, not a mission.** `source_content_identity` hashes the primary `Data/` tree plus one locale tree; `active_content_identity` either verifies a web package and returns its `native_content_sha256`, or hashes the loose tree, and refuses overlays (`content_identity.rs:84-177`). The converter sets the manifest's `native_content_sha256` from `source_content_identity(&data_in)` (`convert_datadir.rs:419-431`); the guest compares it to the ticket on both paths (`multiplayer_content.ts:342-344`, `:382-388`).
- **Claim: `mission_id` is signed but is not used by the current content verifier.** The content verifier reads only `content_edition` and `content_identity_sha256` (`multiplayer_content.ts:375-396`). Mission equality is enforced later on the wire: `WelcomeData.mission_id` must match admitted content's `mission_basename` (`client_protocol.rs:100-115`), and the native host checks the same for a hosted full mod (`multiplayer/native/server.rs:544-546`). That is too late to prove *preloaded bytes* belong to the invited mission.
- **Design requirement (not implemented):** the host must sign a per-mission bundle digest over a canonical list of `(path, byte_length, sha256)` plus `engine_version`, `native_content_sha256`, `mission_id`, `edition` and, if dynamic roster dependencies are included, the roster/closure identifier. The guest proves exactly that set before boot. Concretely this means a new signed field (working name `mission_bundle_sha256`) in `BrowserJoinTicketPayload`, a `JOIN_TICKET_SCHEMA` bump (3 → 4) in both `join_ticket.rs` and `wasm-www/runtime-contract.json`, and a per-mission manifest the guest can hash. `content_identity_sha256` should stay as the whole-closure provenance anchor: a guest holding one mission cannot recompute it, so the host signature must bind the bundle digest *to* that anchor, not replace it. Domain-separate the bundle digest from `CONTENT_IDENTITY_DOMAIN` (`content_identity.rs:38`) to avoid cross-protocol reuse.
- **Unproved:** the exact field name and canonical serialisation; whether replay/highscore `content_manifest_id` bindings (`crates/robin_highscores/migrations/0001_initial.sql:59`, `:86-103`) need a mission-scoped variant; whether a continued campaign session needs a save-world flag signed too.

## 4. Incremental download on mission 2

- **Claim: today the Full guest has no incremental path.** `loadExactFull` verifies and installs *every* file in the selected package before `wasm_boot`, and `preloadLocalShippingFiles` feeds all of them to wasm without yielding so a network fallback is impossible (`multiplayer_content.ts:326-373`; `boot-lifecycle.ts:96-121`; `main.ts:303-315`). Switching missions in a campaign reuses the already-installed bytes in wasm, but the initial download is the whole package.
- **Claim: the Demo path is incremental over HTTP in principle.** `fetch` checks preloaded files, then early downloads, then `GET {base}/{relative}`; the shipping index remains the authority for admissible paths (`browser.rs:133-172`; `shipping_mission.rs:214-253`). The base URL comes from the signed Demo blob's directory (`multiplayer_content.ts:214-219`). Nothing in the repo currently implements the Cache-API-by-digest storage ADR 0005 proposes, and `fetch` does not verify a digest of the returned bytes — it relies on format decode. (Unproved: whether HTTP caching headers from the published origin are enough for current Demo traffic.)
- **Claim: the reusable set is large.** Shared RHS chunks, terrain, common effects, exclamation metadata and voice chunks are content-addressed and named by multiple mission refs (`shipping_datadir.rs:390-400`; `docs/COMPRESSION.md:429-447`). The measured cold path through mission 1 is ~41.65 MB (wasm+JS gzip 4.63 MB, boot datadir 9.35 MB, boot game payload 14.19 MB, 59 mission files 26.14 MB, played audio 1.32 MB) (`docs/COMPRESSION.md:811-837`).
- **Claim: mission 2's new bytes are the mission core plus its unique audio.** Under the schema-v8 split, terrain is shared content-addressed, audio is fetched at first playback, and mission refs add exact ambiance/minimap/PAK/RHS/music (`docs/COMPRESSION.md:803-825`). So the incremental unit is roughly one `missions/*.rhmission.zst` + the mission-specific `rhs/`/`terrain/`/`audio/` paths absent from the cache; the boot datadir, wasm, shared chunks and already-played audio are reusable. ADR 0005's digest-keyed Cache API makes this explicit; browser caches are advisory, so a miss must re-fetch from the origin.
- **Unproved:** the measured mission-2 delta for a current fullgame conversion, and whether a browser preserves the cache across a campaign's mission transitions in practice.

## 5. Hard blockers

- **Licensed data.** Retail/Demo source installations are third-party, not redistributable: `docs/DATADIRS.md:33-243` (demos) and `:253-528` (retail images) list external acquisition only. The Full path therefore asks the user to select a local folder (`multiplayer_content.ts:296-317`); only the Demo closure is published as a blob (`verify-datadir-corpus.mjs:287-296`). A per-mission Full bundle served from a public origin would need a licensing decision; the engine/artifact itself is separately pinned by commit (`multiplayer_content.ts:164-171`).
- **Whole-package verification.** The exact-file-set checks in `verify_web_content_package` and `loadExactFull` reject any subset (`content_identity.rs:341-345`; `multiplayer_content.ts:350-353`); this is deliberate fail-closed behaviour and must be replaced, not bypassed.
- **No digest check on HTTP split-file fetch.** `browser.rs:133-172` trusts the body and relies on decode; a per-mission HTTP path must verify each file against the signed catalog before installation, or a proxy/origin can swap bytes.
- **Save/profile data.** A decoded save adds the conservative `saved_world_rhs_files` closure (`planning.rs:118-125`; `shipping_datadir.rs:102-106`); team and gang rosters further change the closure (`planning.rs:50-117`). The ticket does not sign a save-world flag or roster, so a guest joining a continued campaign may need files the signed bundle omits.
- **Missions outside the converted closure.** `plan_missions` skips profiles with empty `proto_level_filename`/`mission_filename` and warns on missing `.rhp`/`.rhm` (`mission_planning.rs:276-291`); native "hackable" loose-file levels bypass `ensure_shipping_mission` (`game_session/mission_launch.rs:682-706`), and hosted full mods travel as `DistributedModOffer` with their own `mission_basename` (`client_protocol.rs:100-115`; `native/server.rs:544-546`). A retail-data bundle cannot cover arbitrary mods or loose levels. A separate ignored test asserts original-install actor dependencies resolve, but it is not part of any gate (`mission_planning.rs:46-116`).
- **Audio and video.** Cinematics are split into `cinematics/assets` files (`convert_datadir.rs:1651-1668`); schema-v8 audio is lazy Opus with authoritative durations (`docs/COMPRESSION.md:803-825`), and the two Ogg/Theora cinematics retain their original Vorbis tracks (`docs/COMPRESSION.md:763-767`). These are licensed bytes too; the guest cannot fetch them from a public origin without the same licensing decision.

## 6. Recommended design (phases)

1. **Expose the closure.** Emit a canonical per-mission catalog from `dependency_plan.missions[*].destination_payloads` / `dd.missions[*].files` plus the roster and saved-world sets; add a test asserting every `required_dependencies` path belongs to some mission's authored closure. No behaviour change.
2. **Manifest schema v3.** Add the catalog (or one manifest per mission) with per-file digests, bump `WEB_CONTENT_MANIFEST_SCHEMA`, `contentSchema`, `parseLocalManifest`, `parseWebContentManifest`, and replace "exact whole package" with "exact signed bundle". Keep canonical JSON and sorted paths.
3. **Ticket binding.** Add `mission_bundle_sha256` and bump `JOIN_TICKET_SCHEMA` in Rust and TS. Host signs `(engine_version, native_content_sha256, mission_id, mission_profile_id, edition, bundle digest)`. Guest verifies signature, then bundle digest, then every file, then manifest-to-ticket mission/identity equality — before `wasm_boot`.
4. **Guest delivery.** For Full, install only the signed bundle via `wasm_preload_shipping_file` (and lazy audio via `wasm_preload_asset`); for Demo, add digest verification to the HTTP `fetch` path. Store verified bytes under a digest-keyed versioned Cache API name as ADR 0005 specifies; a cache miss re-fetches from the host/origin and re-verifies.
5. **Campaign transitions.** On mission change, compute the next bundle, install only the difference, and keep shared RHS/terrain/audio cached. Fail closed if any required path is absent or has the wrong digest.

## 7. Tests that would prove correctness

- **Missing file fails closed:** a signed bundle with one `rhs/` file removed makes guest preparation fail before `wasm_boot` (extend `multiplayer_content.test.ts` and a `verify_web_content_package` test in `content_identity.rs`).
- **Wrong mission fails:** a guest given mission B's bundle with mission A's ticket fails the `mission_id` binding check before boot; wire-level `WelcomeData` mismatch already covered by `client_protocol.rs:100-115`.
- **Tampered bytes fail:** every file's length and digest is checked, including files fetched over HTTP in the Demo path (`multiplayer_content.ts:319-324`; add the missing check to `browser.rs:133-172`).
- **Cache reuse:** two missions sharing an RHS chunk download it once; second mission requests only its delta. Needs a browser Cache API test with a deliberately evicted entry proving re-fetch.
- **All native missions loadable:** for every CPF mission with a converted payload, `required_dependencies` resolves and installs (turn the ignored `original_missions_have_resolvable_actor_dependencies` test in `mission_planning.rs:46-116` into a gated suite, and add a replay launch for each converted mission).
- **Save-world and roster:** a continued campaign with a non-default party loads the saved-world and character closures; omission fails explicitly.
- **Schema pinning:** old schema-2 manifests and old tickets are rejected; engine-commit mismatch rejected (`content_identity.rs:315-319`; `multiplayer_content.ts:259-261`).

## Ranked next steps

1. Decide licensing: can a per-mission Full bundle be served from a public origin, or must it stay a user-selected folder? This gates phase 4.
2. Emit the per-mission catalog from the existing converter data and gate the "all converted missions resolve" test.
3. Design and bump the manifest + ticket schemas together; keep `content_identity_sha256` as the provenance anchor.
4. Implement guest-side bundle verification before `wasm_boot` and add the digest check to HTTP split-file fetch.
5. Add the Cache API layer and measure the real mission-2 delta on a current fullgame conversion; replace the 2026-08-28 numbers in `docs/COMPRESSION.md` cited here with that measurement.
