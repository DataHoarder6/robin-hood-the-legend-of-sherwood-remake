# Autonomous development loop — design

Date: 2026-11-23. Status: proposed, pending owner approval.
Source of decisions: a four-round grilling with the owner on 2026-11-22/23,
recorded in `/tmp/opencode/autonomy-decisions.md`. Research:
[`docs/research/sandcastle-evaluation.md`](../research/sandcastle-evaluation.md)
and the estate fact sheet on existing automation primitives.

## Intent

One bounded, unattended loop for the robin-hood-remake repo. It draws from a
curated work queue, batches ready items into one tree, runs the single gate,
lands via `scripts/land.sh`, and publishes a MINOR release when the batch is
release-worthy. A human sets the rules in a pre-run contract; the loop never
changes them mid-run and never asks a question mid-run.

The vocabulary is fixed in [`GLOSSARY.md`](../../GLOSSARY.md): work item, work
queue, contract, run, batch, release, promotion, terminal state, run end.

## Goals

- Unattended progress on low-risk items without occupying the owner.
- One gate per batch, reusing the hardened `land.sh` / `push-gate.sh` / ADR 0009
  machinery rather than reinventing it.
- Full observability: manual start, read-only attach, explicit stop.
- Releases are reproducible and recoverable: new tags only, MINOR bumps only,
  two prior AppImages retained, a `robin-pin` the loop cannot touch.

## Non-goals

- No other repo. Not `~/home`, `nixos-config`, infra, or any machine.
- No mid-run questions; no autonomous change to the contract or to steering.
- No auto-install on a seat, no launching the game, no moving an existing tag.
- No MAJOR version bump (first digit of `0.x.0` is human-only).
- No Sandcastle dependency. (Evaluation: pre-1.0 API churn, two recent
  sandbox-escape fixes, host git ignores repo hooks, and it solves none of the
  hard parts — queue, promotion, batched gate, landing read-back, release.)
- No paid model fallback; no cost cap (owner chose none).

## Approaches considered

1. **Build on the robin loop** (director/builder/reviewer/verifier,
   `UNATTENDED.md`, ADR 0009) — *chosen*. The expensive, tested safety half is
   here: four scoped roles, one gate in flight, FIFO landing with remote
   read-back, terminal-state doctrine, and a fully-specified batch design.
2. **Adopt Sandcastle** — rejected. It is a worktree+sandbox execution library,
   not a policy layer; its templates merge branches with an LLM and ignore repo
   hooks. At most useful for per-task isolation later, not now.
3. **Reuse the generic unattended-jobs dispatcher** — rejected as the loop
   itself. It is live (system timer, 31 jobs across other repos) but only files
   GitHub issues and never lands or releases. Its canary, ledger, and
   `ready-for-human` pattern are borrowed as *notifications*.

## The contract (fixed before each run)

A separate pre-run session — not the director, which keeps `question: deny` —
interviews the owner and writes `docs/AUTONOMOUS_RUN_CONTRACT.md`. It contains:

- scope: `robin-hood-remake` only;
- authority: full autonomy (gate, land, tag, publish) — an explicit, ADR-backed
  deviation from `UNATTENDED.md:56` ("a stable tag is human work");
- work-queue rules and the promotion classifier;
- bounds: 4 h wall clock, max 3 batches, no cost cap;
- safety: a per-gate timeout (fail the batch closed) and a circuit breaker that
  halts the run after two consecutive red gates or bisects that yield no landing
  — both standard in GitHub's merge queue and bors;
- release policy: MINOR bumps only (`0.x.0`), never MAJOR; new tags only;
- readonly observation; manual start; stop via `runbg`/API.

The contract is committed and re-read at startup. The loop may not edit it.
A new interview happens only when the owner changes the contract or asks.

## Work queue and promotion

`docs/AUTONOMOUS_BACKLOG.md` is authoritative. Items carry a risk class:

- `proposed:` — generated by the loop when the queue is empty, or filed by a
  reviewer. Cannot be worked until promoted.
- `ready:` — workable this run.
- `needs-work` / `rejected` — reviewer verdicts.

The loop may promote **only** docs, tests, and small refactors. Gameplay,
schema, protocol, release, deletion, and version items stay `proposed:` for the
owner. The risk classifier reuses the path→suite signals in
`scripts/push-gate.sh`.

## Terminal states and run end

The four iteration terminal states are LANDED, FILED, BLOCKED, and
**NEEDS-DECISION**. The last one halts the run and is allowed only for: an
irreversible action the contract does not authorize, two conflicting contract
clauses, a missing external permission, or any ambiguity that would change what
the contract means. It is for rare, brittle, major questions — not routine
ambiguity, which is a contract defect fixed at the next interview. `BLOCKED`
remains capability-only (Windows seat, token).

Release outcomes are tracked separately from the four iteration states:
`RELEASED` (tag pushed, workflow dispatched) and `ROLLED-BACK` (pinned to the
previous good AppImage). They are not iteration terminal states.

A run ends in `RUN-COMPLETE` when a bound is hit (after the current batch) or
when no independent work remains.

## Batch + gate + land

Implement ADR 0009 literally from `docs/research/batched-agent-builds.md`:
readiness refs keyed by head SHA, FIFO epochs, `git merge-tree` conflict
preflight, controller-owned staging tree, **one** tree-keyed gate, bisect on red.
Landing is `scripts/land.sh` with remote read-back. No change to
`push-gate.sh`, `remote-check.sh`, `land.sh`, or the builder/verifier no-push /
no-merge / no-land rules.

## Release

`scripts/auto-release.sh` preflights `verify_release_tag.sh`, refuses if the
tag exists, verifies the bump is MINOR-only, then `git tag -a` + `git push fork`
+ `gh workflow run native-release.yml --ref <tag>`. The MINOR bump and the
"releasable?" decision are derived from Conventional Commits in the batch, not
from agent judgment — the norm in `release-please` and `semantic-release`. It
never runs the machine-repo pin / `apps-sync` step (`RELEASES.md:88-91`) and
never installs or launches. `scripts/appimage-retain.sh` keeps the last two
known-good AppImages; `robin-pin` is owned by the owner and denied to the loop.
An explicit rollback command and a `previous-good` pointer sit beside `robin-pin`.
A spend meter and alert record tokens/cost per run without imposing a hard cap
(the owner chose no cap).

## Operation

- Start: `runbg run autonomy -- bash scripts/autonomy-driver.sh`.
- Observe: `opencode session list`, `opencode session export <id>`, a status
  file. No takeover in v1.
- Stop: `runbg stop autonomy`; freeze the current step via
  `opencode api POST /api/session/<id>/interrupt`.
- Before the first manual run: stop + disable the existing `director-loop.timer`
  (it is #49-only and would compete for worktrees and the gate slot).

## Implementation order (the five smallest changes)

1. `docs/AUTONOMOUS_RUN_CONTRACT.md` (pre-run interview) + `scripts/run-bounds.sh`;
   amend `UNATTENDED.md` terminal-state and goal paragraphs.
2. `docs/AUTONOMOUS_BACKLOG.md` + `scripts/autobacklog.sh` (next-ready,
   generate-proposed, promote, verdict); narrow reviewer/verifier write permits.
3. `scripts/batch-controller.sh` implementing ADR 0009.
4. `scripts/auto-release.sh`; amend `UNATTENDED.md:56`, `director.md:47`,
   `RELEASES.md:84-87`; new ADR for the autonomy deviation.
5. `scripts/appimage-retain.sh` + `robin-pin`; release-worthy predicate in the
   batch controller.

## Verification / smoke test

After 0.5.0 lands, one low-risk item (docs or a test), manual start, read-only
attach, stop via `runbg stop`, verify the contract file and a clean landing.
No release in the smoke test.
